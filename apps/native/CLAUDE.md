# CLAUDE.md — meals_client/apps/native

The native client (Expo / React Native, `expo-router`) for Meals 2.0. Shares
`packages/core` (design tokens, TanStack Query hooks, auth orchestration) with
`apps/web`. Read `../../../SPEC_MOBILE.md` for the client architecture and
`../../../SPEC.md` for product direction.

## Identity and config

- Android package `com.harding.meals_android_client`; iOS bundle
  `com.harding.meals-ios-client`; URL scheme `grub` (`app.json`, `app.config.js`).
- Expo SDK 56, React Native 0.85.
- The native projects are generated by prebuild — `android/` (and `ios/`) are
  gitignored, so they are build output, not source. The source of truth is
  `app.json` / `app.config.js` plus config plugins; do not hand-edit `android/`
  expecting it to persist.

## Running the app on a device

The dev device is a physical phone on **wireless adb** (`adb devices -l` shows a
transport like `..._adb-tls-connect._tcp`, not a USB serial). `adb` is at
`~/Library/Android/sdk/platform-tools/adb` and is not on PATH by default:

```
export ANDROID_HOME="$HOME/Library/Android/sdk"
export PATH="$ANDROID_HOME/platform-tools:$PATH"
```

Two host processes back the app, each reached from the phone through an
`adb reverse` tunnel (the device's own `localhost:<port>` is forwarded to the
host port):

- `meals_server` (Spring Boot) on host `:8080` — the API. `adb reverse tcp:8080 tcp:8080`.
- Metro (Expo dev server) on host `:8081` — JS bundle + fast refresh. `adb reverse tcp:8081 tcp:8081`.

`adb reverse` forwarding works over wireless adb (verified by tunnelling a
scratch port and seeing the host receive the device's request). The phone talks
to `localhost:8080` / `localhost:8081`; it does **not** use the host LAN IP —
Metro answers only on localhost and the LAN IP is firewalled (a request to
`<lan-ip>:8081` times out). So the reverse tunnels, not `expo start --host lan`,
are the working route.

Start Metro:

```
cd meals_client/apps/native
npm start            # = expo start; the live dev session uses: npx expo start --port 8081 --clear
```

Produce or refresh the installed dev build (the debug APK on the device):

```
npm run android      # expo run:android — prebuild (autolinks native modules), build, install, set adb reverse, launch
```

or, when the native project already exists and only a rebuild+install is needed:

```
cd android && ./gradlew :app:installDebug    # requires ANDROID_HOME; gradle 9.3.1 wrapper, JDK 21
```

## Updating the app — the rule that bites

- **JS / TS changes**: Metro serves them. Save for fast refresh, or press `r` in
  Metro / shake → Reload. No rebuild.
- **Native changes** — adding a dependency with native code, editing
  `app.json` / `app.config.js`, config plugins, icons/splash, permissions —
  require a native **rebuild + reinstall** (`npm run android` or
  `gradlew :app:installDebug`). A Metro reload cannot add native code.

Evidenced failure mode (this is easy to hit): adding `react-native-svg` and
`react-native-pager-view` and then only reloading JS crashed the app with
`Can't find ViewManager 'RNSVGPath' in ViewManagerRegistry` — Metro served JS
that referenced a native ViewManager the installed APK did not contain. The fix
is a rebuild, not a JS reload. Whenever `package.json` gains a dependency that
ships native code, rebuild before testing on the device.

## Debugging on the device

`adb logcat` is the device-side source of truth. Cut the noise:

```
adb logcat -d | grep -iE 'ReactNativeJS|AndroidRuntime|FATAL|IllegalViewOperation|was not found'
```

- A JS redbox surfaces as `ReactNativeJS` / `unknown:ReactNative`.
- A missing native module surfaces as `IllegalViewOperationException` /
  `requireNativeComponent ... not found` → rebuild (see above).
- `Unable to load script` / "make sure you're running Metro" means the device
  can't reach Metro: check `adb reverse --list` includes `tcp:8081`, and that
  Metro answers `curl -s localhost:8081/status` → `packager-status:running`.
